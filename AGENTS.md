# Project rules

## Design and contracts

- Follow KISS: choose the simplest construction that solves the observable problem; do not add architectural layers for formal flexibility alone.
- Follow DRY and SSOT: do not duplicate rules, lifecycle, identifiers, state, policy, schemas, transition tables, or algorithms. Each must have one owner; OpenSpec design/spec/tasks and code facades/adapters may refer to that owner and add only their independent responsibility.
- Follow SRP: every layer, entity, and module has one independent responsibility. A facade does not duplicate the lifecycle or state of the underlying runtime; it adds only its own role.
- Apply SOLID where needed: separate stable contracts from implementations, do not couple clients to unnecessary capabilities, and direct dependencies towards abstractions only where that makes replacement or testing simpler. Prefer thin facades over an existing contract rather than parallel registries and state machines.
- Follow YAGNI: do not introduce an entity, layer, abstraction, dependency, or policy engine until a concrete scenario needs it and cannot be solved without it.
- Treat an installed operator skill as a compact workflow contract, not an eval transcript. It MUST contain only instructions needed by an operator to use the admitted MCP surface safely and recover from its material failures; keep fixture literals, fault plumbing, oracle mechanics, and test-only evidence in their single eval/test owner. A hosted eval MAY prove the skill contract, but MUST NOT justify extra prose, duplicate workflow branches, or context-consuming instructions with no operator scenario.
- Any architectural complexity MUST have a brief explanation of the observable problem it solves, why the existing construction is insufficient, and how its necessity is validated by a test or operational scenario.
- Before expanding use of an external or dependency contract, a reviewer MUST confirm its current version, exact schema/API, and applicable capability boundary from a primary source or the installed interface. Unconfirmed fields, methods, and semantics do not belong in the design/spec: keep them behind a narrow version-specific adapter with a golden fixture, or explicitly exclude them from scope.
- Modify existing files with targeted patch hunks. Do not delete and recreate an
  entire file when the requested result can be achieved with local edits; full
  replacement is allowed only for a new file or when the user explicitly asks
  for a complete rewrite.

## Threat model and authority

- Check that the threat model is realistic for an ordinary local Codex + Cursor scenario under one user; do not portray scope validation as a sandbox or security boundary.
- Use technical constraints as protection against scope mistakes only to the degree that they actually constrain process capabilities.
- Do not introduce a policy engine without an explicit need. The MCP server does not make permission decisions automatically; Codex must confirm Cursor actions within authority granted by the user. Do not require one-time-only confirmation when the user has already authorized the full class of actions.
- Escalate scope expansion, destructive and external actions, and credential access when they are outside the user's already granted authority. Apply existing scoped authorization, including the hosted-eval authorization below, without requesting it again. Do not grant indefinite permissions by default.

## OpenSpec convergence

`AGENTS.md` is the single normative owner of project-wide OpenSpec governance. `openspec/config.yaml` may only provide supported OpenSpec configuration and a context link; a change baseline lives in its `design.md` and indexes, rather than repeats, normative requirements in its `spec.md`.

- Before every full review, every change MUST have a `## v1 Contract Baseline` in `design.md`: goal, non-goals, index of public invariants by requirement ID, owner map, implementation-ready exit criterion, and future-change candidates.
- After baseline freeze, every reviewer finding MUST be classified exactly once: `baseline_violation` (minimal repair in the current change), `implementation_concern` (task/test only), `external_adapter_drift` (version-specific adapter/golden fixture only), `new_scope` (separate change), or `overengineering` (remove or exclude from v1).
- Review completeness is not capped, but the number of findings never expands a frozen baseline. An architect MUST validate every classification, repair minimality, and absence of new duplication; `new_scope` needs an explicit user baseline update before entering the current change.
- A normative rule has one owner: runtime owns lifecycle/state/MCP wire/limits; facade owns only user-workflow composition; package owns installation/discovery and one minimal release canary. Upper layers reference owner requirement IDs and test only their independent responsibility.
- Cursor/ACP/Codex schemas, argv, flags, capability details, and versions require primary-source or installed-interface confirmation and belong in a version-specific adapter/golden fixture, not a long-lived product requirement.
- `openspec validate --strict` is structural only. Before review, run the deterministic semantic gate: owner map, no normative duplicates, proposal/design/spec/tasks consistency, and no upper-layer reference to a lower owner's internal details.
- A change is specification-ready when an independent critic finds no `baseline_violation`; `implementation_concern`, `external_adapter_drift`, and future scope do not invalidate the frozen v1 contract.
- For a scoped fix, first reconcile the work with the current frozen baseline, then analyze and apply the minimal repair; run the targeted verification only after the repair is in place, unless a pre-change reproducer is necessary to establish the defect.

## Review

- Before implementation, check every contract for unnecessary entities, unverifiable guarantees, false security claims, and realistic failure paths in ordinary use.
- Do not cap a reviewer's time, number of findings, or verdict size: the review MUST list every discovered blocker and material risk, not only the highest-priority ones.
- Do not interrupt or restart a reviewer before its verdict. This is allowed only for a proven hang or deadlock: the reviewer is explicitly unable to provide the expected result after its actual state has been checked. A timeout observation or transient network errors alone are not such proof. If network errors repeat several times over a meaningful period (minutes), the problem may be considered proven.

## Release notes

- Write release notes in English: start with a short paragraph explaining the release, then use `Features` and `Bug fixes` sections with concise bullets for included changes. Omit empty sections; avoid an unstructured wall of bullets.
- For the first public release, describe the tool's purpose, available features, and practical user benefits instead of only the latest incremental changes.
- Omit verification descriptions and results, test counts, coverage metrics, audit reports, and internal completion bookkeeping.

## Running tests and coverage

- Organize tests as a pyramid by the behavior and dependency boundary actually exercised, not by filename, lane name, or a fixed numerical ratio. Keep a broad base of fast unit/component checks for validation, transformations, facade composition, oracles and classifiers; a smaller set of deterministic integration checks for ACP/MCP, subprocesses, signals, pipes, filesystem and adapters; and a minimal package E2E path for install, discovery, installed-payload execution and cleanup. Run live compatibility canaries and hosted model-behavior evaluations separately from that deterministic base. A fake provider in a real child process does not make a process/stdio integration test a unit test.
- Test each behavior at the lowest layer that can prove it faithfully. Keep pure helper checks out of expensive E2E/eval-only files; retain real process, transport, installation and compatibility checks where those boundaries are the subject. Do not replace them with mocks merely to obtain a pyramid shape. Splitting a file for scheduling is independent of separating test levels. The supervisor owns executable lane membership; use only its implemented commands, and do not present a proposed lane as available or a renamed suite as a completed migration.
- Follow DRY, SSOT and SRP in tests: each semantic scenario has one test owner at the appropriate layer. Upper-layer tests may traverse the same workflow and assert the outcome needed to prove their own integration boundary, but MUST NOT repeat the lower owner's full behavior matrix. Before adding, removing or merging tests, compare current test bodies, inputs, assertions, dependency substitutions and failure paths. For each deletion, identify the retained owner of every material assertion; merge unique assertions before removing duplicate setup. Similar names, identical error codes, shared setup, or equal coverage do not prove duplication: default versus injected adapters, separate pagination sources, retention versus eviction, and terminal versus pending states can exercise different contracts. Keep shared fixtures/helpers with one test owner and do not create a test-only API in product code.
- Ordinary deterministic verification MUST remain independent of credentials, installed live CLIs and external services even when live flags are inherited. The supervisor must isolate all applicable opt-ins, including `CLAUDE_MARKETPLACE_CANARY` and `CURSOR_MODEL_DISCOVERY_LIVE`, and admit them only on an explicitly selected compatible live/eval path. Local loopback fixtures remain deterministic integration. Lane isolation is separate from user authorization. A package scenario may be selected by the eval harness to prove its own package/evidence integration; do not remove that route merely because the same test file is also admitted by the release lane.
- Base performance claims on comparable completed runs: record the runtime/environment, selected suite, executed/skipped scenarios, actual concurrency, wall time and slow file/scenario timings. Use multiple successful baseline and candidate runs with equivalent required behavior coverage; label calculations and single/failed-run timings as estimates or diagnostics. Diagnose ambient stderr/preload/proxy interference before accepting a baseline; do not hide failures with broad warning suppression or weaker assertions. Report focused feedback time separately from the complete required verification cost; moving tests to another command, skipping them, or shrinking the coverage denominator is not a full-suite speedup.
- Optimize measured bottlenecks before raising concurrency. Split long sequential files into cohesive responsibility groups and balance them by observed duration; more file slots cannot eliminate a single long file's critical path. Keep tests that mutate `process.env`, global clocks/timers or process hooks sequential within a process unless those mutations are removed. Prefer isolated per-test environments and process-separated files; give concurrent fixtures independent paths and lifecycles. Parallelize independent fixture I/O only after verifying that it does not share mutable artifacts or publication order. Do not add scheduling frameworks or dependencies without a demonstrated need.
- Replace elapsed-time waits with controlled clocks or explicit readiness/completion signals when testing deadline logic. Preserve assertions about real pipe closure, signals, child termination, cleanup and late-result races where those are the contract; establish readiness before advancing a deadline. Do not shorten product limits, use arbitrary smaller sleeps, reuse mutable sessions across independent scenarios, or weaken boundary cases to meet a timing target.
- Check test brittleness explicitly when adding or reviewing tests, and fix discovered fragility in the same change. Assert observable contracts rather than incidental environment details, exact dependency patch versions, timing, paths, ordering, or internal structure unless the contract requires them. A fixture's recorded version documents its provenance; it does not require the executing runtime to match. Verify runtime compatibility through real integration behavior, and keep any supported-version policy with its existing owner rather than duplicating it in fixture tests.
- Do not weaken product-code coverage when adding, removing, merging or reorganizing tests. Keep at least 90% for lines, branches, and functions in a complete fail-closed manifest of the agreed product scope: source must not disappear from the denominator merely because tests no longer load it. Coverage is a cross-cutting check over the complete admitted deterministic unit/component and integration suite, not a pyramid level or a substitute for behavioral evidence. After test deletion, relocation, helper changes or concurrency changes, run the complete deterministic suite and coverage gate, preserving scenario ownership and examining the raw counters as required below. Every test MUST verify observable behavior, a public contract, or a realistic failure path. Coverage alone is not a reason to add a test; do not add artificial tests for insignificant branches merely for the metric. The exclusion policy below applies to genuinely unreachable defensive code only.
- Exclude individual lines from Node coverage only after classifying them as genuinely unreachable in the admitted product flow. Prefer the narrowest supported directive, `/* node:coverage ignore next */` or `/* node:coverage ignore next N */`; use `/* node:coverage disable */` / `/* node:coverage enable */` only for one minimal contiguous region that cannot be expressed clearly with `ignore next`. Every exclusion MUST have an adjacent rationale stating why the code cannot execute under the supported contract and how the relevant surrounding behavior is verified. An import-only coverage limitation may justify excluding a CLI entrypoint guard only when that same entrypoint is exercised by a separate foreground verification command. Never exclude a meaningful contract, a realistic dependency/error/race path, dead code, a whole product file, or code solely to satisfy a percentage threshold: add or extend a behavioral test for the first two and remove dead code. Treat line and branch exclusion as independent evidence: on the supported Node 22 runtime an ignore directive can remove executable lines from the line denominator while the corresponding zero-count branch remains in the raw report. After changing an exclusion, rerun the full coverage lane, inspect lines, branches, and functions separately, and classify every residual zero-count counter; passing aggregate thresholds alone does not validate the exclusion.
- Run tests in the foreground and consider a run successful only after the command finishes with exit code `0` and its final TAP summary. Do not use `&`, redirect a verification run to a background log, or treat partial output as pass evidence.
- Run every Node test invocation through `node scripts/run-node-tests.mjs`; direct `node --test` is not an admitted verification path. Select only a test admitted by that lane, for example `unit --test tests/runtime-lifecycle.test.mjs`; add `--test-name-pattern <pattern>` for a focused name filter. A focused run that executes zero tests is a failure.
- Run deterministic eval tests through the supervisor, for example `node scripts/run-node-tests.mjs eval --test tests/codex-client-integration.test.mjs`. Run an authenticated hosted model comparison separately in the foreground as `CURSOR_EVAL_HOSTED_CODEX=1 node scripts/eval/run-cursor-skill-eval-matrix.mjs <model> <effort> <absolute-output.json>`; retain its atomically published JSON result and never treat progress JSONL as a verdict.
- When adding, moving, removing, or changing evaluator dependencies, update the existing `EVALUATOR_INPUTS` inventory in `scripts/cursor-skill-eval.mjs` in the same change. The evaluator digest MUST cover the transitive repository inputs used by its admitted lanes, including dynamically loaded adapters, preloads, fixtures, catalogs, and schemas; listing only their importing parent is insufficient. Inputs already bound by a separate evidence digest retain that owner. Keep one inventory owner and exclude host-specific paths and credentials. Extend the existing digest-mutation test for each newly admitted non-skill input: changing it alone MUST change the evaluator digest while leaving the skill digest unchanged. Before declaring ready to archive, a reviewer MUST check the changed import/read/spawn dependency paths against that inventory or their separate evidence owner; passing tests or an unchanged aggregate digest alone do not prove inventory completeness.
- Run authenticated hosted evals outside the filesystem/network sandbox: they require DNS and egress to the Codex endpoint. This is an explicitly authorized external-evaluation step; pass only the isolated materialized scenario, installed skill, and temporary eval workspace. Keep credential-free lanes sandboxed unless their local loopback provider requires the corresponding local bind permission.
- Build a new hosted model baseline with `CURSOR_EVAL_MATRIX_SERIAL=3`: retain all three complete 24-scenario runs, stable corpus and skill digests, the atomic aggregate, every per-run artifact, the actual concurrency, aggregate counts, and each run's counts. Call a configuration reproducibly green only when all three runs pass; otherwise preserve the measured failure distribution instead of selecting a single green run. Progress JSONL and retry-hidden results are not baseline evidence.
- When a change expands the operator-facing Codex/Claude skill or MCP surface, cover every new happy path and material recovery boundary at its owning layer. Extend the credential-free package E2E or scenario eval corpus for the independent installed-package or operator-workflow responsibility, reusing the minimal canary where possible rather than copying the runtime matrix. Before release verification, check the installed `skills/**/SKILL.md` as an operator contract: its workflow, tool names, mode/authority boundaries and close/resume guidance MUST match the admitted MCP surface; a digest-only installation check is insufficient.
- For the current local regression suite, use the supervisor lane below. Its historical name `unit` currently includes deterministic integration tests; it is not evidence that all admitted files are unit tests. New tests and suite migrations MUST follow the pyramid and isolation rules above; this description of current membership does not waive them.

  ```sh
  node scripts/run-node-tests.mjs unit
  ```

- For the same fixed suite with coverage, use `node scripts/run-node-tests.mjs coverage` (the legacy `run-unit-coverage.mjs` remains only as a compatibility entrypoint). For release verification, use `node scripts/run-node-tests.mjs release`. The supervisor owns the process group, waits for `close`, prints a terminal verdict, and writes `tap.txt`, `stderr.txt`, `failures.jsonl`, and an atomic `result.json` to the reported artifact directory. For a non-pass verdict, read `result.json` first, then the references listed there. For a `coverage_gate` verdict, after `result.json` read the last `test:coverage` event in `failures.jsonl`: its per-file `lines`, `branches`, and `functions` with zero `count` are the primary source for locating uncovered lines, branches, and functions. The complete raw report MUST be the review work queue, not optional diagnostics: before completing the change, classify every uncovered point as a meaningful contract, realistic failure path, genuinely unreachable defensive branch, or dead code. For the first two, MUST add or extend a behavioral test; dead code MUST be removed; only genuinely unreachable defensive code may be excluded, with a local justification next to the exclusion or in the review. The 90% threshold is only the minimum fail-closed gate, not the goal, readiness criterion, or reason to stop analysis: passing the aggregate percentage while meaningful branches or lines remain unexamined is incomplete work. New tests must still verify an observable contract or realistic failure path, not a specific line or configuration.
- Run package release, real-Codex, and hosted-auth acceptance as separate foreground commands. Those acceptance runs are outside the deterministic coverage aggregate and cannot substitute for it; pure helper tests extracted from their harnesses belong to the deterministic suite under the same ownership rules.
